Six lessons, each with something to try

1. A miss is slower than having no cache

A read that finds its key is answered by Redis alone. A read that does not must ask Redis first and the database second, so it costs more than if Redis were not there. The fair comparison is never "Redis versus the database"; it is database only versus Redis + database. On average the cache wins only while the hit rate is above Redis latency ÷ database latency. Below that the average read gets slower, and you pay a monthly bill for the slowdown.

Then raise the memory until the Change row in the latency table turns green.

2. Cache size is a hidden TTL

When memory is full, LRU evicts the key that has gone unread the longest. In steady state that means a key is evicted once it has been idle for a fixed time, the eviction age, which follows from the memory size and the traffic (Che’s approximation). So every key lives under two clocks: your TTL, counted from when it was cached, and the eviction age, counted from its last read. Whichever rings first removes the key.

This puts memory and TTL in the same unit, seconds, and explains two wastes. A TTL far above the eviction age does nothing for cold keys, because eviction gets there first. A TTL far below it empties the cache before memory fills, and the memory you bought stays idle.

Watch Memory used, then lengthen the TTL until the eviction age tile stops saying ∞.

3. The median moves, the tail does not

Hits make the typical read fast. But as long as more than 1% of reads miss, the slowest 1% of all reads are misses, and a miss is still a database read with a Redis round trip on top. With a miss rate m, the P99 you see is the database’s (1 − 0.01 / m) quantile: at 20% misses that is the database P95, not far from its P99. If the goal is tail latency, a cache with a merely good hit rate will disappoint.

Compare the P50 and P99 columns of the Change row.

4. Staleness follows the hot keys, not the write ratio

If writes only go to the database, a cached value stays wrong until its TTL fires. How often that happens to a key depends on how many times it is rewritten during one TTL, that is, its own write rate × TTL. Popular keys tend to be written most, so they are rewritten many times per TTL, and they are also the keys that serve most reads. One write per hundred reads with a one hour TTL can leave most reads stale. The remedies both cost misses: a shorter TTL, or deleting the key on every write.

Shorten the TTL, then switch On write to invalidate, and watch stale reads trade against misses.

5. A cache that carries the load is a dependency, not an optimisation

Once the database is sized for the traffic that gets past the cache, it can no longer survive without it. If Redis fails or restarts empty, every read falls through at once, the database saturates, requests time out, and the cache cannot refill because the reads that would fill it are failing. The system can stay in that state after the original fault is gone (Marc Brooker calls it the sad loop of a bimodal system), and load tests rarely find it because they run with a warm cache.

Try it: drag DB capacity below Reads and look at the Redis down figure in the DB load tile, then lower Availability and watch the timeout enter P99.

6. Redis is a database first: its defaults are not cache defaults

Out of the box maxmemory-policy is noeviction: when memory fills, writes fail, nothing new is cached and the hit rate quietly decays as keys expire. A cache needs allkeys-lru or a similar policy chosen on purpose. Redis’ LRU is approximate (it samples 5 keys and evicts the idlest), which tracks true LRU closely. Expired keys are removed lazily on access plus by a background sweep, so they can hold memory a little longer than this model assumes. And a GET does not refresh a TTL, which is why lesson 2 needs two clocks.

Assumptions & non-goals
  • Independent reference model: stationary Zipf popularity, Poisson arrivals; no bursts, trends or temporal locality.
  • All objects have the same size, plus 100 B of per-key Redis overhead.
  • Redis runs allkeys-lru as exact LRU with immediate expiry. Real Redis samples 5 keys and expires lazily, and its default policy is noeviction, which rejects writes once memory is full.
  • The TTL is set when a key is filled and is not reset by hits, unlike the classic Che TTL cache.
  • Writes follow the read popularity. ttl-only: writes go to the database only and the cached copy stays stale until it expires or is evicted. invalidate: writes delete the cached key.
  • Latencies are log-normal fits to P50/P99. A miss pays Redis P50 plus the database; while Redis is down every read pays the client timeout plus the database.
  • Database latency does not grow with load; overload is reported as utilisation only.
  • Non-goals: key design, penetration / avalanche / stampede, multi-tier caches, replica lag, variable object sizes, non-stationary traffic.
